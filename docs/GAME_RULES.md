| 3枠目 | 3,500円 | 構想。決済実装未確認 |

ログイン、村への所属、チャットの主体はユーザー。最初の妖精には次のルールを適用する。

| 項目 | 現行コードの判定 |
|---|---|
| 作成できる人 | 所属村があり、`characters.user_id` が自分のユーザーIDに一致する妖精が0体のユーザー |
| 得意分野 | `App\Enums\CharacterSpecialty` の狩猟系（`Hunting = 1`）または採集系（`Gathering = 2`）から1つ |
| 名前 | 必須、16文字以内、重複可。前後の空白を除いて十進数字だけの名前（例：`1２3`）は使用不可。英数字混在・漢字・カタカナ・ハングル・ひらがなを使える。画面はUnicodeコードポイント単位で数え、作成APIでも長さと数字のみの判定を行う |
| 保存先 | 1体目は `slot = 1`。所有者と滞在村はサーバーが決め、作成時の `users.village_id` を `characters.village_id` に保存する |
| 再送 | すでに妖精がいれば既存の所有一覧を返す。初回作成APIで2体目が増えることはない |
| GM予約表記 | 一般のキャラクター作成では、大文字と括弧を含む `【GM】` が名前のどの位置にあっても拒否する |

## 2. マップ・開拓・移動

### 企画上の基本ルール

- 世界のマップ上をH3セル単位で移動できる構想。
- 海・山は移動不可ではなく**高コスト**とする構想。
- セルに開拓度があり、訪問回数などにより移動係数が減り、移動が容易になる構想。
- キャラクターの体力、行軍値、仲間、装備・お守りなどが距離やコストに影響する構想。

### ソースにある土台

- `resources/js/pages/world/map/config.ts`: `H3_RESOLUTION = 8`、初期中心点、ズーム・ピッチなどの画面設定。
- `resources/js/pages/world/map/h3Grid.ts`: 選択されたセルをH3境界からGeoJSONとして描画。
- `resources/js/pages/world/map/registeredHexLayer.ts`: APIから登録済みセルを取得し描画。
- `terrains.movement_cost`: 地形の基本移動係数（migrationの初期値は `1.0`）。
- `terrains.can_pass`, `villages.can_pass`: 通行可否フラグ（DB定義あり）。**「全マップ航行可能」という構想とどう統合するか要確認。**
- `villages.level`, `villages.points`: DBカラムあり。ただしこれが開拓度や精霊樹レベルを意味するとは断定しない。
- `village_neighbors`: H3セル間の隣接情報を表現するテーブル。

### 未定の計算要素

以下のパラメータの式や適用順序は未確定。`基本コスト × 地形 × 開拓度 × 装備` のような式を**実装済み仕様と決めつけない**。

- コストと体力消費の関係
- 地形・開拓度・行軍値の計算順序
- 仲間数による移動距離補正
- 海・山の具体係数と上限
- 開拓度の共有範囲（ユーザー・村・世界全体）
- 訪問判定（GPS、仮想移動など）
- H3 resolution 8を正式なゲーム解像度として固定するか

## 3. アイテムの種類

企画上、狩猟／採集で別々のアイテムを獲得する。レア・ノーマルの組み合わせ、共通激レア1種、特定地点固有のアイテムを想定する。

**未決定:** 「それぞれレア・ノーマルアイテム4種」の分類・総数、レア発生率、固有アイテムの発生条件、在庫上限、収集可能間隔など。

## 3-1. 村・妖精の滞在・収集物の回収・奉納【方針確定／ゲーム処理未実装】

| 項目 | 新しいルール | 確定度・実装状況 |
|---|---|---|
| 村の単位 | H3セル1個を1村とし、居住対象の村にはそれぞれ精霊樹を置く | 方針確定・精霊樹未実装 |
| 所属村 | **ユーザーが所属村を1つ持つ**。未所属なら登録済みH3セルを選び、初回入村を確定する | 初回入村と村チャットの所属判定は実装済み。移籍・奉納は未実装 |
| 妖精の村 | **所属ではなく滞在**。所属村と異なる村を採集拠点にできる | 方針確定、移動・滞在変更API未実装 |
| 村チャット | ユーザー所属村の住民だけが参加。妖精の滞在村のチャットには参加できない | チャット判定変更 |
| 移動時間 | ユーザー本人にも妖精にも移動時間が必要 | 基本方針確定、計算と移動APIは未定 |
| 素材の所有 | 収穫した素材はまず収集した**妖精のインベントリ**へ入り、自動納入されない | 方針確定、在庫未実装 |
| カバンの上限 | 妖精のカバンは**重量制**。鉱石等は重く、往復回数が増える | 重量制のみ確定、数値は未定 |
| カバンの閲覧 | 派遣中でもユーザーが内容を確認できる | 方針確定、画面未実装 |
| 回収 | 妖精が**ユーザーの所属村へ帰還**してから荷物を受け取れ、回収品は**ユーザー倉庫**へ移す | 方針確定。回収操作の自動／手動は未定・在庫未実装 |
| 廃棄（無課金） | 遠征先では捨てられない。所属村へ帰還後に処理できる | 方針確定、実装なし |
| 廃棄（課金） | 課金特典を利用すれば**遠征先でも廃棄可** | 方針確定、価格・購入形態は未定 |
| ユーザー倉庫 | **ユーザー自身に紐づく重量無制限の倉庫**。妖精の重量制カバンと別管理 | **採用確定**。具体的なDB／API未実装 |
| ユーザーの村移籍 | **倉庫の在庫は同じユーザーに付いて移動**。旧村への置き去り、在庫消失、移籍時の自動奉納はしない | **方針確定**。移籍処理は未実装 |
| 奉納 | ユーザーが**倉庫から**選んだ素材だけを**現在の自分の所属村へ手動奉納**。妖精のカバンから直接奉納せず、他村への奉納や自動奉納なし | 方針確定、API未実装 |
| 精霊樹の成長 | 種類・レア度で獲得成長価値が異なる。欲しい品を**週替わり**にする | 方針確定、点数・曜日・倍率未定 |
| 滞在村ボーナス | 滞在する利点・効率ボーナスを設けたい | **検討中**、内容未定 |

**操作の順序:** 妖精を遠征村へ移動 → 周辺で収集 → 重量上限まで保持 → 移動時間をかけて**その時点のユーザー所属村**に帰還 → ユーザーが荷物を回収して**自分の倉庫へ保管** → 必要なアイテムだけ倉庫から現在の所属村の精霊樹へ手動奉納。**ユーザーが村を移籍しても倉庫は同一ユーザーの持ち物であり、中身はそのまま維持する**。

**用語の区別:** 「移籍／住民票」はユーザーの所属村変更、「派遣／滞在／帰還」は妖精の採集行動。現在地・ユーザー所属村・妖精滞在村は異なる情報として扱う。`characters.village_id` は暫定的に滞在村の格納先として残し、将来の名前変更は別判断とする。

**サーバー判定時の要件:** 実装時は妖精カバンの所持重量・所有者、廃棄可否（有料権限）、帰還完了、ユーザー所属村、**ユーザー倉庫の所有者と保有数量**、週替わりの評価ルールをサーバー側で確認する。回収時は**妖精在庫の減算とユーザー倉庫への加算**、奉納時は**倉庫在庫の減算と所属村への寄与**をそれぞれ一貫した取引として処理し、同時実行・二重送信による複製や二重奉納を防ぐ。ユーザー移籍による倉庫の所有者付け替えは不要。API・DB設計は未決定。

**追加で決める必要があること:** 実際の移動の開始／完了、出発・帰還・再派遣の操作、ユーザーが所属村を変更できる条件、妖精の最大重量、素材ごとの重量、満杯時に収集可能か、帰還後の回収が自動か手動か、倉庫の種類数・スタック制限・倉庫内アイテムの廃棄条件、移籍中の倉庫操作可否、移籍途中で妖精が帰還する場合の行先、無課金の妖精カバン廃棄ルール、課金解放範囲、週次切替の基準時刻・対象アイテム・寄与の倍率。

## 4. 仲間との収集時の報酬【開発者提示の構想】

### 狩猟キャラクター

1. 狩猟系素材を**必ず1個**獲得する。
2. ボーナス抽選: **50%**で採集系素材を追加1個。
3. さらにボーナス抽選: **25%**で狩猟系素材を追加1個。
4. 最大獲得数は**3個**。

### 採集キャラクター

狩猟キャラクターの逆。つまり、採集系素材1個を基本とし、狩猟系素材50%の追加、採集系素材25%の追加を想定する。

**要確認:** 50%と25%の抽選は独立か、条件付きか。上記は仕様文の構造を整理したもので、分布や期待獲得数を確定するものではない。**実際の独立性が決まるまで、期待値・テストの正解値は決めないこと。** レアリティ抽選との順序、仲間ボーナスの増え方も未定。

## 5. 仲間との移動・準備時間【構想】

- 準備期間: **30分**という案。
- 準備中に相乗りメンバーを募集可能。
- メンバーによって準備期間を短縮できるという案も存在。
- 仲間によって獲得通貨・アイテム・開拓恩恵・移動距離が増える構想。

**仕様の衝突:** 「30分準備期間が必ず必要」と「メンバーは準備期間を短縮できる」。最低30分が必須なのか、初期30分で下限付き短縮が可能なのかを決める。

## 6. チャット形式 — ユーザー主体の仕様（今回コード変更）

| 対象 | 入力形式 | DB/enum上の型 | 現時点の送信API |
|---|---|---|---|
| 現在地の村 | 無指定 | `VillageLocal = 1` | 未対応。ユーザー現在地の定義を要再検討 |
| **ユーザー所属村** | `# 本文` | `VillageMember = 2` | **対応**（`users.village_id` が必要） |
| 全体 | `** 本文` | `Global = 3` | 対応 |
| **ユーザー宛DM** | `@ユーザー公開ID 本文` | `Direct = 4` | **対応**（`users.text_id` で宛先特定） |
| 都道府県 | `* 本文` | `Prefecture = 5` | 未対応 |
| 同盟 | `## 本文` | `Alliance = 6` | 未対応 |
| 周囲3セル | `! 本文` | `Nearby3 = 7` | 未対応 |
| 周囲6セル | `!! 本文` | `Nearby6 = 8` | 未対応 |

**宛先IDと資格:** チャットの送信者＝ログインユーザー（`user_id`）。個人宛先＝`users.text_id` で検索したユーザーの `id`（`recipient_user_id`）。キャラクターIDや操作中キャラクターの有無は個人DMに影響しない。DMの自分宛は禁止。茶禁はユーザー単位。

**送信制限:** `POST /api/chat/send` は `auth:sanctum`、`throttle:15,1`。**本文は1〜100文字**（全体・所属村・ユーザー宛DM共通）。`**`、`#`、`@ユーザー公開ID` と区切りスペースは本文100文字に含めない。`message` パラメータ全体は最大360文字（公開ID指定を含む）。指定なしのチャット等、未実装の記号は全体へ誤配信せずエラーとする。

**履歴:** `GET /api/chat/messages` は未ログインなら全体のみ、ログイン済みなら全体・ユーザー所属村・自分の送受信DMを最大200件返す。旧DMも既存の `chat_messages.user_id` / `recipient_user_id` から表示可能。旧メッセージにユーザー公開IDスナップショットがない場合は、現在の公開IDをフォールバック表示（当時の値を復元したとは扱わない）。

## 7. チャット配信・アクセス制御【今回コード変更】

- 全体チャット: 公開 `chat.global`。
- DM: **非公開 `chat.user.{userId}`**。送信者と受信者のユーザーID宛に各1回配信。購読認可は自分の `users.id` と一致するかで判定。
- 所属村: **非公開 `chat.village.{villageId}`**。購読認可はログインユーザーの `users.village_id` と一致するかで判定。妖精の滞在先は無関係。
- イベント名は `.chat-message`。配信payloadにはユーザー公開ID・宛先ユーザーID等のみ含め、IP・User-Agentは含めない。
- 従来の `chat.character.{characterId}` は新規イベント配信と画面での購読を終了する。旧キャラクター別カラムは過去データを守るため削除しない。
- **既存アカウントの `users.village_id` はmigrationで自動補完しない。** 未所属なら `/world` で本人が入村を確定すると、その村のチャットを利用できるようになる。
- 所属村移動後、購読済みの旧村チャンネルを確実に解除する仕組みは今後の所属村変更APIと同時に設計する。

## 8. 経済・課金【構想】

- 旅行・探索で通貨を貯める。
- 通貨でアイテムを購入する。
- 取引機能はサブスク契約者のみ利用可能という案。
- 課金対象として通貨・チケット・キャラ枠・オリジナルアイテム制作の案がある。

トランザクション、購入履歴、価格、通貨発行量、運用制限などの具体設計は未決定。ソース上にこれらのAPIは確認できなかった。

## 9. 実装前に決めること（最優先）

1. 初回入村後に所属村を変更できる条件と手順、移動時間と現在地の扱い（H3セル1村は方針確定）。
2. 訪問判定の方式（現地GPSかゲーム内の旅か）。
3. 未対応チャット種類（通常・都道府県・同盟・周辺）の定義と、ユーザーの現在地に基づく参加資格。
4. 移動と開拓度の式、データの共有範囲。
5. レア抽選・共同収集ボーナスの確率定義。
6. 課金・取引の一貫性と、不正対策の要件。
7. 妖精の重量上限、素材重量、滞在ボーナス、**ユーザー倉庫の具体的な操作・スタック制限**、課金廃棄、週替わり奉納倍率。
