# Hivee — ゲームルール・数値仕様

> 更新日: 2026-11-15  
> 情報源: 開発者が示したルール案 + 2026-11-05のソース。  
> **重要:** 「設計案」「コード上の定義」「送信API実装済み」を混同しない。未定の計算式を補完しない。

## 1. キャラクター

| 項目 | 企画上の値 | 状態・補足 |
|---|---|---|
| 所有可能枠 | 最大3枠 | 構想。DBには `characters.slot`、ユーザー×枠のunique制約あり |
| 2枠目 | 1,500円 | 構想。決済実装未確認 |
| 3枠目 | 3,500円 | 構想。決済実装未確認 |
| 2・3枠セット | 4,500円 | 構想。決済実装未確認 |
| 狩猟の能力 | 素材収集時間10%短縮 | 構想。計算式適用処理未確認 |
| 採集の能力 | レア素材獲得率10%の恩恵 | 構想。加算か乗算か要確認 |
| 体力 | 移動距離に影響 | 値・回復条件・消費式は未定 |

ソース上の区分: `App\Enums\CharacterSpecialty` では `Hunting = 1` / `Gathering = 2`。`characters` は `user_id`、`slot`、`text_id`、`name`、`specialty` 等を持つ。操作中キャラクターは `users.active_character_id`。

## 2. マップ・開拓・移動

### 企画上の基本ルール

- 世界のマップ上をH3セル単位で移動できる構想。
- 海・山は移動不可ではなく**高コスト**とする構想。
- セルに開拓度があり、訪問回数などにより移動係数が減り、移動が容易になる構想。
- キャラクターの体力、行軍値、仲間、装備・お守りなどが距離やコストに影響する構想。

### ソースにある土台

- `resources/js/pages/world/map/config.ts`: `H3_RESOLUTION = 8`、初期中心点、ズーム・ピッチなどの画面設定。
- `resources/js/pages/world/map/h3Grid.ts`: 選択されたセルをH3境界からGeoJSONとして描画。
- `resources/js/pages/world/map/registeredHexLayer.ts`: APIから登録済みセルを取得し描画。
- `terrains.movement_cost`: 地形の基本移動係数（migrationの初期値は `1.0`）。
- `terrains.can_pass`, `villages.can_pass`: 通行可否フラグ（DB定義あり）。**「全マップ航行可能」という構想とどう統合するか要確認。**
- `villages.level`, `villages.points`: DBカラムあり。ただしこれが開拓度や精霊樹レベルを意味するとは断定しない。
- `village_neighbors`: H3セル間の隣接情報を表現するテーブル。

### 未定の計算要素

以下のパラメータの式や適用順序は未確定。`基本コスト × 地形 × 開拓度 × 装備` のような式を**実装済み仕様と決めつけない**。

- コストと体力消費の関係
- 地形・開拓度・行軍値の計算順序
- 仲間数による移動距離補正
- 海・山の具体係数と上限
- 開拓度の共有範囲（ユーザー・村・世界全体）
- 訪問判定（GPS、仮想移動など）
- H3 resolution 8を正式なゲーム解像度として固定するか

## 3. アイテムの種類

企画上、狩猟／採集で別々のアイテムを獲得する。レア・ノーマルの組み合わせ、共通激レア1種、特定地点固有のアイテムを想定する。

**未決定:** 「それぞれレア・ノーマルアイテム4種」の分類・総数、レア発生率、固有アイテムの発生条件、在庫上限、収集可能間隔など。

## 3-1. インベントリ・村の移籍・手動奉納【基本方針確定／未実装】

| 項目 | 基本ルール | 状態 |
|---|---|---|
| インベントリの所有者 | キャラクターごとに収穫アイテムを保持する | 基本方針確定、実装なし |
| 収穫後の保存先 | 収穫したアイテムは獲得したキャラクターのインベントリに入る | 基本方針確定、実装なし |
| 自動納入 | 収穫時・村移籍時に村への自動奉納は行わない | 基本方針確定、実装なし |
| 村の移籍 | キャラクターは別の村へ移籍し、再び元の村へ移籍できる | 基本方針確定、実装なし |
| 未奉納品の扱い | 村を移籍してもキャラクターのインベントリに残り、持ち運べる | 基本方針確定、実装なし |
| 奉納の実行 | プレイヤーがインベントリから対象アイテムと数量を指定し、明示的に奉納する | 「手動操作」は確定、UI詳細・数量仕様は要設計 |
| 奉納先 | 奉納操作時の**所属村**。近接しているだけの別村や、以前所属していた村に自動では納めない | 基本方針として整理、実装なし |
| 奉納の結果 | 奉納成功分をキャラクターの保有数から減らし、奉納先の村の精霊樹の育成に寄与させる | 基本方針確定、成長計算は未定 |

**想定する一連の行動:** 旅先の村へ移籍 → 周辺で狩猟・採集 → インベントリで持ち運ぶ → 地元の村へ戻って移籍 → 地元の村に手動奉納。旅先の村へ奉納するか持ち帰るかはプレイヤーの選択とする。

**用語の区別:** 「所属村」は奉納先を決める村、「現在地」は地図上のキャラクター位置。「地元の村」は帰郷先を説明する言葉であり、恒久的な本籍村の記録が必要かは未決定。現行 `villages` テーブルはH3セル情報を扱うため、この3概念のDB上の関係を実装前に整理する。

**実装に向けた安全要件（設計上の必要条件）:** インベントリ残数・奉納先所属・対象数量をサーバーで再検証し、奉納品の減算と村への寄与を単一トランザクションで原子的に確定する。二重送信・同時操作でアイテムが二重に奉納されないようにする。正確なDBテーブル名やAPI名はまだ決定しない。

**未決定:** カバン容量・重量・スタック上限、満杯時の獲得処理、移籍費用・クールダウン・条件、移籍可能な場所と実際の現在地の制約、奉納可能なアイテム種別と数量単位、精霊樹への寄与計算、奉納取消・履歴、キャラクター間の所持品移動、移籍前後の所属履歴、地元（本籍）村の永続化、収穫と現在地／所属村の関係。

## 4. 仲間との収集時の報酬【開発者提示の構想】

### 狩猟キャラクター

1. 狩猟系素材を**必ず1個**獲得する。
2. ボーナス抽選: **50%**で採集系素材を追加1個。
3. さらにボーナス抽選: **25%**で狩猟系素材を追加1個。
4. 最大獲得数は**3個**。

### 採集キャラクター

狩猟キャラクターの逆。つまり、採集系素材1個を基本とし、狩猟系素材50%の追加、採集系素材25%の追加を想定する。

**要確認:** 50%と25%の抽選は独立か、条件付きか。上記は仕様文の構造を整理したもので、分布や期待獲得数を確定するものではない。**実際の独立性が決まるまで、期待値・テストの正解値は決めないこと。** レアリティ抽選との順序、仲間ボーナスの増え方も未定。

## 5. 仲間との移動・準備時間【構想】

- 準備期間: **30分**という案。
- 準備中に相乗りメンバーを募集可能。
- メンバーによって準備期間を短縮できるという案も存在。
- 仲間によって獲得通貨・アイテム・開拓恩恵・移動距離が増える構想。

**仕様の衝突:** 「30分準備期間が必ず必要」と「メンバーは準備期間を短縮できる」。最低30分が必須なのか、初期30分で下限付き短縮が可能なのかを決める。

## 6. チャット形式 — 企画と現在の実装を分離

| 対象 | 開発者の企画 | DB/enum上の型 | 現時点の送信API |
|---|---|---|---|
| 滞在村 | 無指定 | `VillageLocal = 1` | **未完成／要修正** |
| 所属村 | `# 本文` | `VillageMember = 2` | 未対応 |
| 全体 | `** 本文` | `Global = 3` | **対応**（`**本文` も受理） |
| 個人 | `@` | `Direct = 4` | **対応**（`@公開キャラクターID 本文`） |
| 都道府県 | `* 本文` | `Prefecture = 5` | 未対応 |
| 同盟 | `## 本文` | `Alliance = 6` | 未対応 |
| 周囲3セル | `! 本文` | `Nearby3 = 7` | 未対応 |
| 周囲6セル | `!! 本文` | `Nearby6 = 8` | 未対応 |

実装確認: `app/Enums/ChatMessageType.php`、`app/Http/Requests/Api/StoreChatMessageRequest.php`、`app/Http/Controllers/Api/ChatController.php`。

注意点:

- `ChatMessageType.php` のコメントには全体を `$$`、都道府県を `$` と書いているが、**企画は `**` / `*`、現在の送信パーサーも全体 `**`**。コメントは整合性確認の対象。
- 送信時の内部キャラIDは `users.active_character_id` を基準とし、所有権を確認している。
- 送信時の茶禁チェックがある。茶禁はアカウント単位。
- `POST /api/chat/send` は `auth:sanctum` および `throttle:15,1` が設定されている。
- `GET /api/chat/messages` は全体チャットと、認証済みの場合は自分が送受信したDMを集約する処理がある。最大200件での表示を意図している。
- 現行FormRequestは `message` 全体の `max:100` と、本文の `1〜300` 文字チェックが併存している。**有効な上限は整理が必要。**
- `StoreChatMessageRequest::after()` の未対応メッセージ分岐は `elseif ($raw) {}` の空ブロックになっている。**未定義の `$type` / `$body` を参照しうる**ため、改修時の優先チェック対象。

## 7. チャットの権限・配信【実装観測】

- 全体チャットは公開チャンネル `chat.global`。
- DMは `chat.character.{internalId}` のPrivateChannelを使い、`routes/channels.php` でキャラ所有者だけが購読可能。
- イベント名は `.chat-message`。
- 送信元IP・User-AgentはDBには保持するが、配信payloadでは送らない実装。
- 現在のUIは `resources/js/pages/world/components/panels/ChatPanel.tsx`。複数種を表示フィルタするUIがあることは、各種の送信APIが実装済みであることを意味しない。

## 8. 経済・課金【構想】

- 旅行・探索で通貨を貯める。
- 通貨でアイテムを購入する。
- 取引機能はサブスク契約者のみ利用可能という案。
- 課金対象として通貨・チケット・キャラ枠・オリジナルアイテム制作の案がある。

トランザクション、購入履歴、価格、通貨発行量、運用制限などの具体設計は未決定。ソース上にこれらのAPIは確認できなかった。

## 9. 実装前に決めること（最優先）

1. マップのセルとプレイヤーの所属村の概念・DB関係（移籍先・奉納先の確定に必要）。
2. 訪問判定の方式（現地GPSかゲーム内の旅か）。
3. チャット記号・送信文字数・未対応チャットの段階的な実装方針。
4. 移動と開拓度の式、データの共有範囲。
5. レア抽選・共同収集ボーナスの確率定義。
6. 課金・取引の一貫性と、不正対策の要件。
7. インベントリ容量、移籍条件、奉納可能条件、精霊樹への寄与換算。
